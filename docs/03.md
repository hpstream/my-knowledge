## 开篇：你不需要懂算法，但需要懂"边界"

很多人有一个误区：学 VibeCoding 不需要了解 AI 的内部原理，反正你就是和它说话嘛。

这话对了一半。你确实不需要了解 Transformer 架构，不需要懂反向传播，不需要会调参。

但如果你完全不了解大语言模型是怎么工作的，你就会在一些关键时刻做出错误的判断：

- 明明 AI 上一轮还记得需求，这一轮突然"失忆"了，你不知道为什么
- 同样的问题问两次，AI 给了两个截然不同的答案，你不知道哪个对
- AI 信誓旦旦地告诉你某个函数的用法，你照着写了，运行报错，才发现根本没有这个函数
- 你的提示词越写越长，AI 反而越来越"跑偏"，你搞不清楚问题在哪

这些困惑，都源于对模型工作方式的误解。

这篇文章不是 AI 课，不会深挖技术细节。它的目标是：**用最少的知识，帮你建立一套实用的心智模型**，让你在使用 AI 编程工具时，知道它为什么这样表现，以及怎么应对。

## 一、Token：AI 眼中的"字"不是你理解的字

要理解大语言模型，第一个必须搞清楚的概念是 **Token（词元）**。

### Token 是什么

Token 是大语言模型处理文字的基本单位，但它既不是"字"，也不是"词"，而是介于两者之间的一个文本片段。

举几个例子感受一下：

```
英文单词 "hello"         → 1 个 Token
英文单词 "unbelievable"  → 4 个 Token（un / belie / vable / ...）
中文"你好"              → 约 2 个 Token
中文"人工智能"          → 约 4~5 个 Token
一段 800 字的中文文章    → 约 1000~1200 个 Token
```

中文由于字符密度高，通常 1 个汉字对应约 1~1.5 个 Token。英文则大约每 4 个字符对应 1 个 Token，或者说每 100 个单词约 75 个 Token。

### Token 为什么重要

Token 直接决定两件事：**费用**和**上下文容量**。

**费用**：所有 AI API 按 Token 计费。你发给 AI 的内容（input token）和 AI 回复的内容（output token）都计费。Token 越多，花的钱越多。

**上下文容量**：每个模型都有一个"上下文窗口（Context Window）"，单位是 Token。这是模型在一次对话中能"记住"的最大信息量。超出这个限制，早期的内容会被丢弃。

主流模型的上下文窗口：

| 模型              | 上下文窗口 | 约等于         |
| ----------------- | ---------- | -------------- |
| Claude Sonnet 3.7 | 200K Token | 约 15 万字中文 |
| GPT-4o            | 128K Token | 约 10 万字中文 |
| Gemini 2.5 Pro    | 1M Token   | 约 75 万字中文 |
| Claude Opus 4     | 200K Token | 约 15 万字中文 |

200K 听起来很大，但一个中等规模的代码项目（几十个文件）很容易超过这个限制。所以在 VibeCoding 中，**管理上下文是一项重要技能**，我们会在提示词篇专门讲。

## 二、上下文窗口：AI 的"工作记忆"

理解了 Token，就能理解上下文窗口（Context Window）。

可以把上下文窗口类比成人的"工作记忆"——就是你当下能同时记在脑子里处理的信息量。心理学研究表明，人的工作记忆大约能同时处理 7±2 个组块信息。AI 也是类似的，只不过它的"工作记忆"是以 Token 来衡量的。

### 上下文窗口里装着什么

当你和 AI 对话时，上下文窗口里装的东西比你想象的要多：

```
┌──────────────────────────────────┐
│  System Prompt（系统提示词）      │  ← 工具的内置指令，你看不到
│  CLAUDE.md / 项目配置文件         │  ← 你写的项目说明
│  历史对话记录（你说的 + AI 说的） │  ← 越聊越多
│  当前引用的文件内容               │  ← @file 引入的代码
│  你这一轮发送的消息               │  ← 你的提问
└──────────────────────────────────┘
         总量不能超过上下文窗口上限
```

### 上下文"装满"了会发生什么

当对话轮次增多，或者引用了大量代码文件，上下文会逐渐被填满。不同工具的处理策略不同：

- **截断早期内容**：最老的对话记录被丢弃，AI 开始"遗忘"前面说过的事
- **滑动窗口**：保留最近的若干轮对话，删除更早的
- **摘要压缩**：把历史对话压缩成摘要（质量损失较大）

**实际影响：** 你和 AI 聊了很长时间，突然它开始给出和之前风格不一致的代码，或者忘记了你之前说过的约定。这通常就是上下文溢出的信号。

**应对方法（先记住概念，细节在提示词篇展开）：**
- 长任务拆成多个独立的短对话
- 在每次新会话开始时，简要重申项目约定
- 用 CLAUDE.md 持久化项目背景，不依赖对话历史

## 三、温度参数：控制 AI 的"随机性"

如果你用过 OpenAI API 或 Anthropic API，可能见过一个叫 `temperature`（温度）的参数，取值范围通常是 0 到 2。

这个参数控制的是 AI 输出的**随机程度**：

| 温度值  | 特性                       | 适合场景                     |
| ------- | -------------------------- | ---------------------------- |
| 接近 0  | 输出高度确定，几乎每次相同 | 代码生成、数据提取、格式转换 |
| 0.5~0.7 | 适度随机，稳定中有变化     | 日常对话、代码解释           |
| 接近 1  | 更有创意，但可能偏题       | 文案创作、头脑风暴           |
| 大于 1  | 高度随机，容易胡言乱语     | 几乎不用                     |

### 对 VibeCoding 的实际意义

多数 AI 编程工具已经预设了合适的温度值，你不需要手动调整。但理解这个概念能解释一个让新手困惑的现象：

**为什么同样的问题，AI 每次给的代码不一样？**

答案就是温度参数。即使是低温度，AI 也不是纯粹的确定性系统，它每次采样时都有一定的随机性。这不是 Bug，是设计如此。

**实践建议：**
- 需要**稳定可复现**的结果（比如关键业务逻辑代码），把需求描述得越精确越好，减少 AI 发挥空间
- 需要**探索方案**时（比如让 AI 给几种实现思路），可以让它多给几个方案，挑最合适的

## 四、为什么同一问题 AI 每次回答不一样

这是新手最常问的问题之一，温度参数是一个原因，但不是全部。

### 原因一：采样随机性（温度参数）

上文已解释。即使温度为 0，主流大模型通常也不是完全确定的。

### 原因二：上下文不同

你以为你问的是"同一个问题"，但实际上两次对话的上下文是不同的——历史记录不同、引入的文件不同、甚至日期不同（AI 可能根据时间调整回答风格）。

### 原因三：模型本身在更新

AI 服务提供商会持续更新模型版本，同一个名字（比如"Claude Sonnet"）背后的模型可能已经迭代了。这也会导致相同问题在不同时间得到不同答案。

### 对实际工作的影响

这意味着：**不要把 AI 当成一个精确的工具，而要把它当成一个有能力、但需要你把关的协作者。**

关键代码必须经过你的审查和测试，不能因为"AI 上次说这样写没问题"就永久信任。

## 五、幻觉（Hallucination）：AI 最危险的特性

**幻觉**是大语言模型最重要、也最容易被新手忽视的特性。

简单来说：**AI 会用极其自信的语气，告诉你一件完全错误的事。**

### 幻觉长什么样

以下是一个真实发生过的场景：

一位开发者在用 AI 编写 Python 脚本，需要处理 Excel 文件。AI 建议使用 `openpyxl` 库，并给出了这样的代码：

```python
from openpyxl import load_workbook
wb = load_workbook('data.xlsx')
ws = wb.active
ws.auto_filter.add_filter_column(0, vals=["completed"])
ws.save('output.xlsx')
```

AI 还附上了一句解释："`add_filter_column` 方法可以直接筛选指定列中的特定值。"

开发者照着写，运行后发现根本没有筛选效果。查文档才发现：`add_filter_column` 方法的参数完全不是这么用的，AI 杜撰了一个不存在的用法。

这就是幻觉——**AI 生成了语法上正确、逻辑上通顺、但事实上错误的代码**。它不是在说谎，它只是在"补全"，而补全的内容恰好是错的。

### 幻觉最容易出现在哪里

| 场景                | 幻觉风险 | 说明                                   |
| ------------------- | -------- | -------------------------------------- |
| 第三方库的 API 细节 | **高**   | 版本更新快，训练数据可能已过时         |
| 小众框架或工具      | **高**   | 训练数据少，AI 容易"编造"用法          |
| 具体的版本号、日期  | **中**   | 容易给出不准确的版本信息               |
| 数学计算            | **中**   | 复杂计算容易出错                       |
| 基础语言语法        | **低**   | Python/JS 等主流语言的核心语法很少出错 |
| 通用编程逻辑        | **低**   | 循环、条件判断等基础结构基本可信       |

### 如何应对幻觉

**第一条原则：越重要的代码，越要验证。**

不要因为 AI 说得头头是道就直接用。关键逻辑必须运行测试，外部库的 API 用法建议查阅官方文档确认。

**第二条原则：让 AI 给你信息来源。**

```
# 这样问
这段代码里用到了 openpyxl 的 add_filter_column 方法，
能告诉我这个方法的官方文档在哪里，以及正确的参数格式吗？
```

如果 AI 支支吾吾说不清楚来源，或者给出的链接打开是 404，通常就是在编造。

**第三条原则：用可运行的小例子验证。**

对于不确定的 API 用法，先写一个最小可运行的例子测试，确认行为符合预期，再写进正式代码。

## 六、主流模型的编程能力对比

不同的 AI 模型在编程任务上的能力有差异。了解这一点，可以帮你在不同场景下选对工具。

### 当前主流模型一览（2025 年下半年）

**Claude 系列（Anthropic）**

| 模型              | 上下文 | 编程能力特点             | 适合场景           |
| ----------------- | ------ | ------------------------ | ------------------ |
| Claude Opus 4     | 200K   | 最强推理，复杂架构设计   | 系统设计、复杂重构 |
| Claude Sonnet 4   | 200K   | 速度与能力均衡，日常最佳 | 日常编码主力       |
| Claude Sonnet 3.7 | 200K   | 扩展思考模式，适合难题   | 算法题、复杂调试   |

Claude 系列在**长上下文理解**和**多文件联动修改**上表现突出，特别适合需要理解大型代码库的场景。

**GPT 系列（OpenAI）**

| 模型    | 上下文 | 编程能力特点                   | 适合场景             |
| ------- | ------ | ------------------------------ | -------------------- |
| GPT-4o  | 128K   | 速度快，多模态（支持图片输入） | 截图转代码、快速迭代 |
| o3      | 200K   | 强推理，擅长算法和数学         | 竞赛算法、数据分析   |
| o4-mini | 128K   | 轻量推理，性价比高             | 简单任务、高频调用   |

o3 在**算法推理**和**数学计算**类任务上表现最强，是解 LeetCode 难题的首选。

**Gemini 系列（Google）**

| 模型             | 上下文 | 编程能力特点         | 适合场景         |
| ---------------- | ------ | -------------------- | ---------------- |
| Gemini 2.5 Pro   | 1M     | 超长上下文，整库理解 | 超大型代码库分析 |
| Gemini 2.5 Flash | 1M     | 速度极快，成本极低   | 大批量代码处理   |

Gemini 2.5 Pro 的 **100 万 Token 上下文**是目前最长的，理论上可以把一个中型项目的全部代码一次性喂给它分析。

### 一个实用的模型选择建议

对于 VibeCoding 的日常使用，不需要纠结选哪个模型。遵循这个简单原则：

```
日常编码       → Claude Sonnet（Claude Code 默认）
算法 / 数学    → o3 或 Claude Sonnet 3.7（开启扩展思考）
大型代码库分析 → Gemini 2.5 Pro
快速原型 / 草稿 → GPT-4o 或 Gemini Flash（便宜快）
```

工具会持续更新，今天最强的模型明天可能被超越。**养成在工具中切换模型测试的习惯**，比固执地用同一个模型要实用得多。

## 七、用一张图理解大语言模型的工作方式

把以上内容整合成一张工作原理图：

```
你的输入
  │
  │  （转换为 Token）
  ▼
┌─────────────────────────────────────┐
│           上下文窗口                  │
│  System Prompt + 历史对话 + 你的输入  │
│          总量 ≤ N 个 Token            │
└─────────────────────────────────────┘
  │
  │  （模型逐 Token 预测下一个最可能的词）
  ▼
输出 Token 流
  │
  │  （受温度参数影响，有随机性）
  │  （可能包含幻觉）
  ▼
你看到的回答
```

**核心记住三点：**

1. **Token 是计量单位**，决定费用和记忆上限
2. **上下文窗口是有限的**，对话越长越容易失忆
3. **输出有随机性和幻觉风险**，重要内容必须验证

## 本篇小结

- **Token**：AI 的基本计量单位，中文约 1 字 = 1~1.5 Token，决定费用和上下文容量
- **上下文窗口**：AI 的工作记忆，满了就会"遗忘"，管理上下文是 VibeCoding 的核心技能
- **温度参数**：控制输出随机性，代码生成用低温度，方案探索用高温度
- **为什么每次答案不同**：采样随机性 + 上下文差异 + 模型持续更新
- **幻觉**：AI 会用自信的语气说错误的事，第三方库 API 用法是高发区，必须验证
- **模型选择**：日常用 Claude Sonnet，算法用 o3，超大代码库用 Gemini 2.5 Pro
