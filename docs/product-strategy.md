## 1. 你的洞察值多少分

### 1.1 复述你的核心论点（确保我没误读）

- 大多数知识产品教你「**从打螺丝开始造车**」
- 但当你脑子里有个「**我想要一辆能开的车**」时，前者不解决问题
- 用户卡的不是技术细节，是「**我该准备哪些非代码的东西，从哪里申请**」
- 用户也有可能卡细节,但是我么要给他提供一个现成的方案去用,而不是从头去实现这个方案.
- AI 已经能写代码 → 但 AI 写不出"去微信开发者平台让 朱\*\* 给我授开发者权限"这种线下流程
- 所以人需要的是 **「Recipe + 申请清单 + AI 提示词模板」**，而不是"理解 OAuth 原理"

### 1.2 我的判断：你这洞察是 **8/10 分**

**强的地方**：

- 这个洞察对，而且**反直觉**——市场默认逻辑是"教得越深越值钱"，你看到的是相反方向
- 我刚帮你调研微信登录那 6 轮对话**本身就是这个洞察的直接证据**：技术上不难，卡的全是"哪个微信号有权限/域名要不要备案/IP 在哪里加白名单"
- 你最后选了"先做邮箱登录"，不是因为微信登录写代码难，而是非代码门槛太高 → **这就是市场需求**
- 把"非代码门槛"系统化产品化 = 真实需求 + 有壁垒（壁垒不是技术，是**保鲜的内容运营**，下面会说）

**要警惕的地方**：

- 这个赛道在英文世界已经有人做（Lovable / Bolt 是工具方向；Indie Hackers 社区/英文 Boot­camp 是培训方向）
- **中文市场比较薄、机会窗口在**——但同时意味着市场教育成本高，第一波用户是早期接受者
- 后面 §6 会展开：**内容保鲜是这个赛道的最大风险**

你想给网站加微信扫码登录，已经有备案域名 + 已认证服务号。

- [ ] 已 ICP 备案的中国域名 → 阿里云备案 / 腾讯云备案
- [ ] 你的生产服务器出口 IP → 怎么查 ↗

【你需要去申请的（清单 + 入口 + 截图）】
1. 公众号 AppID + AppSecret

3. 配置 IP 白名单
   - 后台路径：安全配置 → IP 白名单
   - 填：你的服务器出口 IP
4. 配置服务器消息推送 URL（可选，扫码登录可以不要）

## 6. 内容运营：这个赛道的最大风险

### 6.1 风险：内容保鲜成本极高

举例（基于我们本次对话的真实情况）：

- 2025-12-01：微信公众号"开发管理"整建制迁到微信开发者平台
- 如果你 2025-11 发了一篇"微信开发配置教程"，**12-02 当天它就过时了**
- 用户买了发现照着做不通 → 退款 / 差评 / 信任崩塌

类似的"高频变动点"：

| 变动源                   | 频率                      |
| ------------------------ | ------------------------- |
| 微信开发者平台 UI        | 每年小改、3-5 年大改      |
| OpenAI / Anthropic API   | 每 3 个月有新模型、定价变 |
| Vercel / Cloudflare 计费 | 每 6-12 个月有调整        |
| Stripe 跨境政策          | 不定期                    |
| 中国 ICP 备案细则        | 每年                      |

### 6.2 我提的对策（必做）

1. **每个 Recipe 显示"最近更新"日期**，超过 60 天没更新自动标"可能过期"
2. **建社群（微信群 / Discord）做众包反馈**，用户发现过期 → 上报 → 你/团队修
3. **季度全量检查机制**：每季度跑一遍所有 recipe 的"申请清单"链接是否还活着
4. **退款策略明确化**：照着做不通 → 7 天无条件退（用信任换长期复购）
5. **结构化 vs 长文**：Recipe 是结构化的，过期只改几段，长文要重写

## 8. 我个人最大的 3 个顾虑

### 8.1 内容保鲜不是写代码，是体力活

我能给你写代码、写运营系统、写后台。但 **每周 2-3 个 Recipe 的产出**靠你自己（或团队）。
人少的话，节奏要慢下来——质 > 量。一个月只发 3 个 Recipe 但每个都过硬，强于一个月发 10 个一半过期。

### 8.2 中文知识付费用户的"惯性"

中文用户的预期模型是「一次性买完看完拉倒」。
订阅 + 持续运营是英文世界 SaaS 思维，国内还在教育期。

应对：
- 强调"最新"概念——给用户「每周看新 Recipe」的预期
- 不要一开始就推年订阅，先做单买，6 个月后再上订阅

### 8.3 你自己的精力分配

做内容产品 = 70% 内容 + 20% 营销 + 10% 技术。
但你跟我合作时主要在 "技术" 那 10%。
**「技术做好了但内容跟不上」是这类项目最常见的死法。**

应对：
- 我建议你提前规划：每周固定 X 小时写 Recipe，每周固定 Y 小时做 1 条短视频
- 把"产 Recipe"的流程也工业化（我后续可以做模板/工具支持）

## 附录 A：Recipe 格式正式 schema（参考）

```typescript
type Recipe = {
  // 基础信息
  id: string;
  slug: string;
  title: string;
  category: string;        // 登录 / 部署 / 支付 / AI 接入 / 数据合规 / ...
  difficulty: 1 | 2 | 3 | 4 | 5;
  estimatedMinutes: number;
  estimatedCost: string;   // "免费" / "300 元/年" / "$10/月"
  scenario: string;        // 适用场景一段话

  // 准备清单
  prerequisites: {
    label: string;
    detailUrl?: string;     // 跳到详细说明
  }[];

  // 申请清单（核心区分点）
  applications: {
    title: string;
    where: string;           // 入口（域名）
    screenshots?: string[];  // 操作截图
    youGet: string[];        // 你最终拿到的东西
    notes?: string;
  }[];

  // AI 提示词模板（核心区分点）
  aiPromptTemplate: string;

  // 验证步骤
  verifySteps: string[];

  // 常见踩坑
  pitfalls: {
    symptom: string;          // 现象
    cause: string;            // 原因
    fix: string;              // 修复
  }[];

  // 内容保鲜
  publishedAt: Date;
  lastVerifiedAt: Date;       // 最近一次"确认还能用"的时间
  status: "active" | "stale" | "deprecated";

  // 商业化
  pricing: "free" | "paid";
  priceCents: number;         // 价格（分）
  enrollCount: number;        // 已购人数
  averageRating: number;
};

type Course = {
  id: string;
  slug: string;
  title: string;
  description: string;
  recipeSlugs: string[];      // 串联哪些 Recipe
  projectTemplateRepo?: string; // GitHub 项目模板
  estimatedDays: number;
  pricing: "free" | "paid";
  priceCents: number;
};

type Order = {
  id: string;
  userId: string;
  type: "recipe" | "course" | "subscription";
  itemId: string;
  amountCents: number;
  paidAt: Date;
};
```
